# Roblox Debug

## Контекст проекта и инструменты

- Перед работой прочитай актуальные AGENTS.md, README.md и default.project.json; сохраняй чужие изменения. Здесь src/server → ServerScriptService.GarageServer, src/client → StarterPlayerScripts.GarageClient, src/shared → ReplicatedStorage.Garage. Код редактируется в файлах и синхронизируется Rojo; не подменяй его правкой Source через MCP.
- При использовании Studio MCP сначала вызови list_roblox_studios, выбери нужное место и вызови get_studio_state. Используй фактически возвращённый studio_id, а не сохранённый идентификатор. При неоднозначности уточни цель. Не запускай и не останавливай чужой сеанс без необходимости.
- execute_luau всегда направляй в доступный datamodel_type: Edit для инспекции редактора, Server для серверного состояния, Client для локального UI и ввода. При запросе только на анализ или документацию ограничься чтением; не создавай объекты, не запускай Play и не публикуй игру.
- Проверяй API по официальным страницам ниже. Через MCP можно получить руководство skill с skill_name rbx-docs-search и читать http_get по URL документации с окончанием .md. Недоступность инструмента укажи явно; не выдавай предполагаемый результат за выполненную проверку.

## Порядок работы

1. Запиши симптом, ожидаемое поведение, точные шаги, затронутые файлы, режим Studio и сторону выполнения. Сначала собери факты без правок; отдели первичную ошибку от последующих.
2. Проследи путь ввода: клиент → RemoteEvent → серверная проверка → изменение состояния → репликация → UI. Сравни Client и Server; отсутствие объекта при StreamingEnabled не доказывает его отсутствие на сервере.
3. Прочитай Output и stack trace доступным средством Studio. Для сложного сбоя получи через MCP skill rbx-debug и следуй актуальным инструкциям точек останова. Не выдумывай названия debug-инструментов. Снимай только нужные значения; не выводи секреты и полный профиль игрока.
4. Проверь границу доверия. Сервер владеет валютой, инвентарём, наградами, уроном и переходами состояния. Клиент отправляет намерение, а не итоговый баланс или разрешение. В OnServerEvent первый player передаёт движок: не принимай личность игрока из payload. До дорогой работы проверь типы, конечность чисел (NaN/±inf), диапазоны, размеры строк/таблиц, разрешённые ID и принадлежность Instance ожидаемому контейнеру. Затем проверь серверные права, состояние, расстояние и cooldown; применяй серверный лимит частоты на игрока/действие и очищай его при уходе. Не пересылай непроверенный payload другим клиентам. Аннотации типов и клиентский debounce не заменяют runtime-валидацию. В тестовом месте воспроизведи неверные типы, подменённые ID, спам и повтор запроса; не проводи разрушительные эксперименты с боевыми данными.
5. Сформулируй проверяемую гипотезу и меняй по одному причинному фактору. Временные логи и breakpoints обозначь и после проверки убери. Учитывай, что остановка потока меняет тайминги гонок.
6. Для просадок сначала измерь frame time, CPU/GPU и память на одинаковом сценарии; через MCP skill rbx-perf-profiling используй доступный MicroProfiler. Сокращай per-frame работу, объём репликации и утечки, затем повтори измерение. Не называй локальное ощущение измерением.
7. Исправь корень минимальной правкой исходников. Повтори исходные шаги, соседний сценарий, respawn и уход/возврат игрока. Сетевую гонку проверь в Server & Clients с двумя клиентами; при необходимости используй доступную эмуляцию задержки.

## Типичные ошибки

- Исправление UI, когда сервер отвергает действие по правильному правилу.
- Проверка серверного состояния в Client или вывод о двух игроках по одиночному Play.
- Добавление task.wait как универсального исправления гонки.
- Отключение валидации, rate limit или сохранений, чтобы тест «прошёл».
- Сравнение профилей с разным числом игроков, качеством графики или длительностью прогона.

## Критерии проверки

- Причина подтверждена наблюдением; исходное воспроизведение больше не вызывает сбой.
- Защита remotes сохранена, допустимый запрос работает, ошибочный не меняет состояние.
- Нет новых ошибок Output и утечек при повторе; для производительности приведены сопоставимые замеры до/после.
- В итоговом отчёте перечисли изменённые файлы, выполненные проверки с результатами и оставшиеся ограничения. Различай статический анализ, одиночный Play, Server & Clients и реальное устройство.
- Для изменений кода используй существующие StyLua/Selene и TestEZ. scripts/Build.ps1 -Tests также создаёт сборку и может обновить test.project.json: сначала проверь его актуальное содержимое и необходимость перезаписи. В отдельной тестовой сборке, где существует ServerStorage.GarageTests, серверный запуск: return require(game.ServerStorage.GarageTests.Run)(). Ноль выполненных тестов не считается успехом. На этапе создания навыков эти проверки игры не запускай.
