# Roblox Gameplay

## Контекст проекта и инструменты

- Перед работой прочитай актуальные AGENTS.md, README.md и default.project.json; сохраняй чужие изменения. Здесь src/server → ServerScriptService.GarageServer, src/client → StarterPlayerScripts.GarageClient, src/shared → ReplicatedStorage.Garage. Код редактируется в файлах и синхронизируется Rojo; не подменяй его правкой Source через MCP.
- При использовании Studio MCP сначала вызови list_roblox_studios, выбери нужное место и вызови get_studio_state. Используй фактически возвращённый studio_id, а не сохранённый идентификатор. При неоднозначности уточни цель. Не запускай и не останавливай чужой сеанс без необходимости.
- execute_luau всегда направляй в доступный datamodel_type: Edit для инспекции редактора, Server для серверного состояния, Client для локального UI и ввода. При запросе только на анализ или документацию ограничься чтением; не создавай объекты, не запускай Play и не публикуй игру.
- Проверяй API по официальным страницам ниже. Через MCP можно получить руководство skill с skill_name rbx-docs-search и читать http_get по URL документации с окончанием .md. Недоступность инструмента укажи явно; не выдавай предполагаемый результат за выполненную проверку.

## Порядок работы

1. Опиши цикл механики: вход, допустимые состояния, переходы, цена, награда, отмена, смерть и отключение. Прочитай актуальные Rules, Config и серверные обработчики; README может отставать от кода.
2. Размести авторитетную модель на сервере; shared содержит только безопасные общие вычисления/данные. Клиент обрабатывает ввод и эффекты. Если используешь предсказание, предусмотрены серверное подтверждение и откат.
3. Сервер владеет валютой, инвентарём, наградами, уроном и переходами состояния. Клиент отправляет намерение, а не итоговый баланс или разрешение. В OnServerEvent первый player передаёт движок: не принимай личность игрока из payload. До дорогой работы проверь типы, конечность чисел (NaN/±inf), диапазоны, размеры строк/таблиц, разрешённые ID и принадлежность Instance ожидаемому контейнеру. Затем проверь серверные права, состояние, расстояние и cooldown; применяй серверный лимит частоты на игрока/действие и очищай его при уходе. Не пересылай непроверенный payload другим клиентам. Аннотации типов и клиентский debounce не заменяют runtime-валидацию. ProximityPrompt, Touched и ClickDetector также требуют серверных проверок; визуальная близость и клиентские свойства не являются разрешением.
4. Сделай операции списания/награды устойчивыми к повторам и параллельным запросам. Проверь существующие Atomic, Profiles и Rules до расширения. Избегай yield внутри критического перехода или защищай его подходящей блокировкой с очисткой при ошибке. Не дублируй обработчики покупок.
5. Для транспорта и физики учитывай network ownership: клиент может управлять принадлежащей ему сборкой. Проверка расстояния до перемещаемого клиентом объекта сама по себе недостаточна для ценных действий. Сервер проверяет допустимость результата.
6. Оцени стоимость при целевом числе игроков и объектов: события вместо постоянных полных обходов, ограниченные очереди спавна, минимальные payload и частота рассылок. Удаляй временные объекты, соединения и записи состояния при завершении/выходе.
7. Проверь чистые правила TestEZ, затем Play и Server & Clients: два игрока одновременно берут один предмет, повторяют действие, пытаются действовать с чужим объектом, издалека и после смерти. Для заявленной ёмкости проекта в шесть игроков проведи отдельный соответствующий прогон, если среда позволяет.
8. Сохранения проверяй через существующий Studio Mock в Profiles. Mock не подтверждает реальные DataStore; такую проверку выполняй отдельно в предназначенной тестовой среде. Не меняй префиксы/доступ к API и не публикуй без задачи на это.

## Типичные ошибки

- Клиент назначает награду, урон, окончание таймера или владение.
- Двойная выдача предмета из-за одновременных обработчиков или повторного запроса.
- Доверие физике клиентского транспорта как доказательству законного действия.
- Бесконечный спавн, FireAllClients на каждый кадр, отсутствие очистки после выхода.
- Успех Mock объявляется подтверждением сохранения в опубликованной игре.

## Критерии проверки

- Переходы соответствуют правилам; запрещённые действия отклоняются на сервере.
- Конкурирующие/повторные запросы не дублируют награды и списания; отказ не оставляет частично изменённый профиль.
- Состояние согласовано для участников и наблюдателей; смерть, выход и повторный вход обработаны.
- Проверена нагрузка заявленного масштаба либо явно указано ограничение; боевые данные не затронуты.
- В итоговом отчёте перечисли изменённые файлы, выполненные проверки с результатами и оставшиеся ограничения. Различай статический анализ, одиночный Play, Server & Clients и реальное устройство.
- Для изменений кода используй существующие StyLua/Selene и TestEZ. scripts/Build.ps1 -Tests также создаёт сборку и может обновить test.project.json: сначала проверь его актуальное содержимое и необходимость перезаписи. В отдельной тестовой сборке, где существует ServerStorage.GarageTests, серверный запуск: return require(game.ServerStorage.GarageTests.Run)(). Ноль выполненных тестов не считается успехом. На этапе создания навыков эти проверки игры не запускай.
